# 缩略图引用计数与手动清理设计

- 文档版本：1.0
- 日期：2026-07-23
- 状态：已确认，待实施计划

## 1. 背景与目标

当前缩略图以图片内容 SHA1 为缓存键，目录结构为：

```text
<data_dir>/.cache/thumbnails/{sha1[:2]}/{sha1}/{size}.jpg
```

同一内容的多张图片共享同一套缩略图。现有 `POST /api/admin/thumb-cache/purge` 会删除整个缩略图缓存，无法只回收已经不再被图库或回收站引用的缓存。

本功能目标：

1. 记录每个 SHA1 在图库和回收站中的引用数量；
2. 仅由管理员手动触发无引用缩略图清理；
3. 引用仍存在时绝不主动清理对应缓存；
4. 清理历史遗留的孤儿缓存；
5. 保持 8 万张图片规模下的扫描、启动和清理性能；
6. 缩略图意外丢失时继续按需生成，无需重新扫描图库。

## 2. 范围

### 2.1 本次包含

- 新增 `thumbnail_refs` 引用计数表；
- 通过 SQLite 触发器实时维护 `images` 引用计数；
- 在 `trash` 表存在时维护回收站引用计数；
- 首次升级时对已有数据执行一次聚合回填；
- 每次手动清理前批量校准引用计数；
- 将现有全量清空接口改为“只清理无引用缩略图”；
- 清理缓存目录中没有引用记录的历史孤儿目录；
- 管理端按钮、确认提示和清理结果展示；
- 审计、并发控制、异常处理和测试。

### 2.2 本次不包含

- 自动、定时或启动时清理缩略图；
- 缩略图全量预生成；
- 保留“清空全部缩略图缓存”能力；
- 因本功能单独实现完整回收站模块；回收站表和路由仍按其既有阶段计划实施；
- 修改缩略图尺寸或 JPEG 编码质量。

## 3. 当前实现约束

- `images.sha1` 已有索引，并作为缩略图缓存键；
- 缩略图由 `ThumbnailGenerator.ensure()` 按需生成；
- 当前允许尺寸为 200、400、1600；
- 当前数据库通过 SQLAlchemy `Base.metadata.create_all()` 初始化，尚未使用 Alembic；
- 当前代码尚未实现 `trash` 表，但已有后续阶段设计；
- 当前清理接口位于 `routes_admin.py`，使用 `shutil.rmtree` 删除整个缓存目录；
- 缓存删除必须继续遵守路径边界和符号链接安全检查。

## 4. 方案选择

### 4.1 采用：数据库引用计数表

新增一张以 SHA1 为主键的引用计数表。清理时使用集合查询和文件系统目录集合比较，不对每个 SHA1 单独访问数据库。

选择理由：

- 能以主键高效维护计数；
- 一次查询即可获得有效引用集合；
- 易于覆盖重复图片、图库删除和未来回收站操作；
- 适合 8 万张图片规模；
- 清理结果容易审计和测试。

### 4.2 未采用：清理时逐目录查询

逐个遍历缓存 SHA1 目录并分别查询 `images`、`trash` 会产生 N+1 查询。8 万个目录可能对应 16 万次查询，不满足性能目标。

### 4.3 未采用：仅依赖应用代码增减计数

扫描器、级联删除、未来回收站操作都需要记得更新计数，容易遗漏。数据库触发器可以覆盖普通写入与级联删除，并让计数变化与业务数据处于同一事务。

## 5. 数据模型

新增 ORM 模型和表：

```python
class ThumbnailRef(Base):
    __tablename__ = "thumbnail_refs"

    sha1: Mapped[str] = mapped_column(String, primary_key=True)
    image_count: Mapped[int] = mapped_column(Integer, nullable=False, default=0)
    trash_count: Mapped[int] = mapped_column(Integer, nullable=False, default=0)
```

字段语义：

| 字段 | 类型 | 说明 |
|---|---|---|
| `sha1` | TEXT PK | 缩略图缓存键 |
| `image_count` | INTEGER | `images` 表中引用该 SHA1 的行数 |
| `trash_count` | INTEGER | `trash` 表中引用该 SHA1 的行数 |

可清理条件：

```text
image_count + trash_count == 0
```

数据库约束应保证两个计数不小于 0。应用读取时也不得把负数视为无引用证据；手动清理前必须先执行权威校准。

## 6. 引用计数维护

### 6.1 `images` 触发器

Schema 初始化时使用 `CREATE TRIGGER IF NOT EXISTS` 安装以下触发器：

1. `AFTER INSERT ON images`
   - 以 `NEW.sha1` UPSERT `thumbnail_refs`；
   - 已存在时 `image_count + 1`。
2. `AFTER DELETE ON images`
   - 以 `OLD.sha1` 将 `image_count - 1`；
   - 使用下限 0，计数异常不得阻断图库核心操作。
3. `AFTER UPDATE OF sha1 ON images WHEN OLD.sha1 <> NEW.sha1`
   - 旧 SHA1 的 `image_count - 1`；
   - 新 SHA1 的 `image_count + 1`。

触发器覆盖：

- 扫描发现新图片；
- 图片内容变化导致 SHA1 变化；
- 扫描发现图片消失；
- 删除 Root 或图库造成的 `images` 级联删除。

### 6.2 `trash` 触发器

当前代码尚无 `trash` 表。Schema 初始化逻辑只有在检测到 `trash` 表存在时才安装对应触发器：

1. `AFTER INSERT ON trash`：`trash_count + 1`；
2. `AFTER DELETE ON trash`：`trash_count - 1`；
3. `AFTER UPDATE OF sha1 ON trash`：旧值减 1，新值加 1。

未来回收站表通过 `create_all()` 创建后，同一次启动应安装这些触发器。回收站相关测试必须验证：

```text
移入回收站：image_count - 1，trash_count + 1
恢复图片：  trash_count - 1，image_count + 1
永久删除：  trash_count - 1
```

相关业务操作必须在一个数据库事务中完成。短暂的语句级中间状态不可被清理任务观察到。

### 6.3 首次数据回填

升级已有数据库时，在创建 `thumbnail_refs` 及触发器后执行一次聚合回填：

```sql
INSERT INTO thumbnail_refs (sha1, image_count, trash_count)
SELECT sha1, COUNT(*), 0
FROM images
GROUP BY sha1;
```

如果 `trash` 表存在，再按 SHA1 聚合并更新 `trash_count`。

“建表、安装触发器、回填完成”应在一个可恢复的 schema 初始化事务或显式版本标记控制下完成，避免进程在建表后、回填前退出而永久跳过回填。不能仅以“表存在”作为“回填已经完成”的判断依据。

首次回填只执行一次。普通启动不遍历缩略图目录，也不重复执行 8 万行聚合。

### 6.4 清理前权威校准

每次管理员手动清理前，以 `images` 和存在时的 `trash` 为真实来源，批量重建引用数量：

1. 将现有 `thumbnail_refs.image_count` 和 `trash_count` 置零；
2. 使用 `GROUP BY sha1` 批量 UPSERT `images` 聚合结果；
3. `trash` 表存在时批量 UPSERT其聚合结果；
4. 保留两项均为零的旧行，供本次清理定位；
5. 整个校准在单个数据库事务中完成。

该校准可修复旧版本数据、异常退出、触发器缺失或人工修改数据库造成的偏差。实现不得退化为逐 SHA1 查询。

## 7. 手动清理流程

### 7.1 接口

沿用现有路径并改变语义：

```http
POST /api/admin/thumb-cache/purge
```

权限：仅管理员。

旧行为：删除整个缩略图缓存。

新行为：仅清理没有 `images` 或 `trash` 引用的 SHA1 缓存目录，不再提供全量清空模式。

成功响应由 `204` 改为 `200`：

```json
{
  "scanned": 12450,
  "removed": 238,
  "failed": 1,
  "freed_bytes": 987654321
}
```

字段含义：

| 字段 | 说明 |
|---|---|
| `scanned` | 本次检查的合法 SHA1 缓存目录数量 |
| `removed` | 成功删除或确认已不存在的无引用 SHA1 目录数量 |
| `failed` | 因 I/O、安全检查等原因未能清理的目录数量 |
| `freed_bytes` | 成功删除文件的实际字节数总和 |

### 7.2 清理步骤

1. 获取应用内清理互斥锁；若已有任务运行，返回 `409`，错误码 `thumb_cache_purge_in_progress`；
2. 批量校准 `thumbnail_refs`；
3. 一次查询获得所有有效 SHA1：`image_count + trash_count > 0`；
4. 一次查询获得引用表中的零引用 SHA1；
5. 遍历缓存根下合法的 `{2位前缀}/{40位SHA1}` 目录；
6. 缓存目录 SHA1 不在有效集合中时，将其列为清理候选；这同时覆盖引用表零引用记录和历史孤儿缓存；
7. 删除前对候选集合做一次批量引用复核，不允许逐候选查询；
8. 对仍无引用的目录逐个执行安全删除，统计目录数和文件字节数；
9. 删除成功或目录已不存在后，批量删除对应的零引用 `thumbnail_refs` 行；
10. 删除为空的两位前缀目录；
11. 写审计日志并释放互斥锁。

数据库复核与实际文件删除之间仍可能发生引用变化，但缩略图属于可再生缓存：极端竞态只会造成一次缓存未命中，下一次访问会自动生成，不会影响原始图片或数据库数据。应用锁只串行化清理任务，不应长期阻塞扫描器。

### 7.3 文件系统性能

- 数据库操作均为固定数量的集合 SQL；
- 文件系统必须遍历缓存目录，以发现历史孤儿缓存并统计释放空间；
- 目录扫描、字节统计和删除放入工作线程，避免阻塞 FastAPI 事件循环；
- 不读取 JPEG 内容，只读取目录项和文件元数据；
- 不在应用启动、普通扫描或普通浏览时遍历缓存目录；
- 可以分批处理候选 SHA1，避免一次构造过大的 SQL `IN` 参数列表；批大小是实现细节，但不得产生逐项查询。

## 8. 缩略图缺失时的恢复行为

不新增“补全缩略图”扫描任务。现有按需生成逻辑继续作为恢复机制：

```text
GET /api/thumb/{sha1}?size=N
    → ThumbnailGenerator.ensure()
    → 缓存存在：直接返回
    → 缓存缺失：从仍被引用的原图生成并缓存
```

因此：

- 单个或多个缩略图意外丢失后，无需重新扫描图库；
- 用户下次浏览对应图片时自动重新生成；
- 大量缓存丢失时，首次访问可能较慢，但不影响功能正确性；
- 清理操作绝不删除原图。

为避免同一缩略图在缓存缺失时被并发重复生成，`ThumbnailGenerator` 增加进程内按 `(sha1, size)` 去重锁。锁内需要再次检查目标文件是否已经生成。锁对象在任务结束后移除，避免锁表无限增长。

生成文件建议采用同目录临时文件写入，再以原子替换发布，避免并发读取半写入 JPEG。该改动仅增强缓存生成可靠性，不改变 API。

## 9. 并发与一致性

### 9.1 清理任务

- 同一进程同一时刻只运行一个手动清理；
- 重复请求立即返回 409，不排队；
- 清理锁在异常路径也必须释放；
- 本项目为单进程部署，不设计跨进程分布式锁。

### 9.2 扫描和回收站操作

- 引用计数由数据库触发器在同一事务内维护；
- 清理前校准只读取已提交数据；
- 候选删除前使用集合查询复核；
- 极端竞态导致的缩略图误删可按需重建，原图不受影响；
- 不为保证缓存存在而阻塞长时间扫描或回收站事务。

## 10. 路径与安全约束

清理逻辑继续遵守现有红线，并强化为逐目录校验：

1. 缓存根固定为 `<data_dir>/.cache/thumbnails`；
2. 缓存根自身不得是符号链接；
3. 所有候选路径解析后必须位于缓存根内；
4. 仅识别两位十六进制前缀目录和 40 位小写十六进制 SHA1 目录；
5. 不跟随候选目录或内部条目的符号链接；
6. 非法目录名、符号链接、路径逃逸或不可访问目录不删除，计入 `failed` 并记录日志；
7. 清理代码不得接收客户端提供的任意文件系统路径；
8. 任何清理失败不得回退到图库根或原图目录操作。

## 11. 异常处理

采用逐 SHA1 尽力清理：

- 单个目录失败不终止其余候选；
- 目录删除成功或已不存在时才清除对应零引用记录；
- 删除失败的引用行保留为零，下一次手动清理可重试；
- 数据库校准失败时不开始文件删除，并返回 500；
- 缓存根安全检查失败时不删除任何目录；
- 审计写入失败沿用项目现有审计容错策略，但必须记录应用日志；
- 最终响应准确反映部分成功，不把失败报告为全部成功。

## 12. 审计

沿用动作名：

```text
thumb_cache_purge
```

审计 detail 至少包含：

```text
mode=unreferenced scanned=<n> removed=<n> failed=<n> freed_bytes=<n>
```

不在审计中记录全部 SHA1 列表，避免日志过大。失败 SHA1 和异常原因写应用日志。

## 13. 管理端交互

现有按钮由“清空缩略图缓存”改为：

> 清理无引用缩略图

确认对话框说明：

- 只清理已不属于图库且不在回收站中的缩略图；
- 不删除任何原始图片；
- 正在使用的缩略图不会被主动清理；
- 缺失缩略图会在浏览时自动生成。

执行期间按钮禁用，防止前端重复提交。成功后显示：

```text
已清理 238 组缩略图，释放 941.9 MB；1 组清理失败。
```

当 `removed == 0` 时显示“没有可清理的无引用缩略图”。409 时提示已有清理任务正在运行。

## 14. 测试策略

### 14.1 数据模型和触发器

1. 新增图片时 `image_count + 1`；
2. 同 SHA1 多张图片共用一行并正确累计；
3. 图片 SHA1 变化时旧值减一、新值加一；
4. 图片删除时计数减一且不小于零；
5. Root/图库级联删除时计数正确减少；
6. `trash` 表存在时安装对应触发器；
7. 移入、恢复和永久删除回收站图片时两类计数正确；
8. 首次升级对已有图片正确聚合回填；
9. 首次回填中断后能安全重试，不产生重复计数。

### 14.2 校准和清理服务

1. 校准能修复错误计数；
2. 任一引用计数大于零时不删除缓存；
3. 两项均为零时删除该 SHA1 的所有尺寸；
4. 能删除没有 `thumbnail_refs` 行的历史孤儿目录；
5. 相同 SHA1 被多张图片引用时不会误删；
6. 删除成功后移除零引用行；
7. 删除失败时保留零引用行供下次重试；
8. 非法目录名、符号链接和路径逃逸不被删除；
9. 空缓存和不存在的缓存根得到成功的零结果；
10. 释放字节数按实际删除文件统计；
11. 单目录失败不影响其他目录；
12. SQL 调用数量不随 SHA1 数量线性增长，防止 N+1。

### 14.3 API 与审计

1. Admin 获得 200 和完整结果字段；
2. 非 Admin 被拒绝；
3. 并发第二个请求获得 409；
4. 审计包含模式、扫描数、删除数、失败数和释放字节数；
5. 安全检查失败时没有任何文件被删除。

### 14.4 按需再生成

1. 已引用图片的缓存文件缺失时，请求自动生成；
2. 无需重新扫描即可生成；
3. 同一 `(sha1, size)` 并发请求只执行一次渲染；
4. 渲染失败不留下可被当作有效缓存的半成品文件。

### 14.5 前端

1. 按钮和确认文案反映“仅清理无引用缓存”；
2. 请求期间按钮禁用；
3. 正确展示删除数量、失败数量和格式化释放空间；
4. 0 删除结果和 409 有明确提示。

## 15. 验收标准

- 8 万张图片下，引用维护不引入逐图片数据库查询；
- 普通启动不遍历缩略图缓存目录；
- 普通扫描不遍历缩略图缓存目录；
- 手动清理的数据库阶段使用固定数量的集合 SQL；
- 图库或回收站仍有引用的 SHA1 不被主动清理；
- 历史孤儿缓存可被清理；
- 全量清空能力已移除；
- 清理不会访问或删除任何原图；
- 缩略图丢失后可由浏览请求自动再生成，无需重新扫描；
- 管理员可以看到实际清理数量、失败数量和释放空间；
- 所有安全、触发器、API、并发和再生成测试通过。

## 16. 与回收站阶段的衔接

本功能不提前实现完整回收站，但将 `trash_count` 作为正式字段保留。回收站功能落地时必须：

1. 在 `trash` 表创建后的 schema 初始化中安装 `trash` 触发器；
2. 将已有 `trash` 行聚合进 `thumbnail_refs`；
3. 验证移入、恢复、永久删除和到期清理的计数转换；
4. 保证回收站仍引用的缩略图不被清理；
5. 在回收站缩略图路由可访问后，继续使用相同 SHA1 缓存目录。

该衔接要求应同步纳入回收站阶段实施计划，避免后续只创建 `trash` 表却遗漏引用维护。
